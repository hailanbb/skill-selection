## 概述
本 Skill 自动完成 Obsidian 笔记的分类、加工与归档：

1. 读取待整理文件夹中的笔记
2. AI 分析笔记内容，生成结构化 frontmatter 属性
3. 按分类规范将加工后的笔记归档到对应的一级分类文件夹
4. 将原笔记移至已整理文件夹（保留原件）

---

## 首次使用：配置流程
首次触发时，依次询问用户以下信息（一次一问，确认后再问下一个）：

1. **Obsidian 库本地路径** — vault 根目录的绝对路径（如 `D:\MyVault`）
2. **待整理文件夹名称** — 可以有多个，逗号分隔（如 `01 待阅收件箱, 02 Clippings`）
3. **原笔记归档文件夹名称** — 处理完成后，原始笔记移至此文件夹（如 `03 已整理`）
4. **加工笔记归档文件夹名称** — 加工后的新笔记移至此文件夹（如 `06 已归档`）

获取配置后执行以下检查：

- 确认 vault 路径存在，不存在则提示用户修正
- 确认各文件夹存在，不存在则自动创建
- 检查 vault 根目录下是否存在 `obsidian_note_categories.md`：
  - **不存在** → 从本 skill 的 `references/obsidian_note_categories_template.md` 复制一份到 vault 根目录，并告知用户：
    > 已在你的 vault 根目录创建分类规范文件：`{vault路径}/obsidian_note_categories.md`
    > 你可以随时编辑此文件来调整分类体系，Skill 每次运行时会从中读取最新的分类规则。
  - **已存在** → 读取用户自定义的分类体系，以用户版本为准

后续使用时，如果用户再次触发且已知配置，直接进入处理流程，不再重复询问。

### 模式选择
根据用户的表达自动判断模式：

- **批量模式**（默认）：用户说"整理笔记""整理收件箱"等泛指表达 → 扫描所有待整理文件夹中的 `.md` 文件，逐一处理
- **单篇模式**：用户指定了某篇笔记的路径或文件名 → 只处理该篇

### 单篇处理步骤
对每篇笔记依次执行以下操作：

#### 步骤 1：读取笔记

读取笔记 of 完整内容，包括已有的 frontmatter（如果有）和正文。

#### 步骤 2：AI 分析与属性生成

基于笔记正文内容，生成以下 frontmatter 属性：

| 属性 | 生成规则 |
|------|---------|
| `author` | 从已有元数据提取，多个作者用 wiki link 格式（如 `[[作者A]], [[作者B]]`） |
| `description` | 用中文总结核心内容，150 字以内，第三人称视角，直接输出总结文本 |
| `source` | 从已有元数据提取原始 URL |
| `published` | 从已有元数据提取发布日期，格式 `YYYY-MM-DD` |
| `clipped` | 从已有元数据提取剪藏日期，格式 `YYYY-MM-DD` |
| `tags` | 分析文章主题，生成 3-5 个精准的中文标签词，不含 `#` 号 |
| `category` | 按分类规范判定的**二级分类**名称 |
| `key_points` | 提炼 3-5 个核心观点，每个用一句话概括 |
| `quality` | 评估内容质量（信息密度、论证深度、原创性），打分 1-5（5 最高） |
| `related_concepts` | 提取 3-5 个核心概念或知识领域关键词，用于构建知识图谱 |

**元数据与 YAML 格式处理原则（非常重要）：**
- `author`、`source`、`published`、`clipped` 从原笔记已有 frontmatter 中提取，原笔记中不存在则留空，绝不编造。
- 如果原笔记已有部分 AI 生成类属性（`description`、`tags` 等），保留已有值，只填充缺失的属性——不覆盖用户手动填写过的值。
- **YAML 语法极度严格**：生成的所有字符串值（尤其是 `description`、`key_points` 列表项、`related_concepts`），**如果以特殊字符（如反引号 \`、@、%、* 等）开头，或者内部包含冒号（:）、引号，必须使用英文双引号 `" "` 将整个字符串包裹起来**。否则会导致 Obsidian 属性面板解析失败！为了安全，建议对所有包含空格或标点的文本字段进行双引号包裹。
- **避免 Markdown 语法冲突**：虽然属性面板支持纯文本，但在 `key_points` 或 `description` 中尽量减少使用反引号（\`）等标记。如果使用，必须确保外层有双引号包裹，如 ` - "`\cangjie-skill\` 2.0 新增视频..."`。

#### 步骤 3：判定分类

从 vault 根目录的 `obsidian_note_categories.md` 读取分类体系：

- 判定**一级分类**，并从「一级分类 → 文件夹名称映射」表中获取**完整的归档文件夹名称**（含编号前缀，如 `1. 工具推荐`）。绝对禁止省略编号，否则会产生重复文件夹。
- 判定**二级分类**（写入 `category` 属性）
- 每篇笔记只归一个分类，以**主要意图**为准，次要主题通过 `tags` 关联

#### 步骤 4：执行文件操作

1. **文件名预处理（防乱码与 URL 编码）**：
   - **URL 解码**：检测原文件名，如果原文件名被 URL 编码（即包含 `%` 等百分号字符，如 `%E6%88%91...`），**必须进行 URL 解码**，恢复为正常的可读中英文字符。
   - **去除非法字符**：清除 Windows 和 macOS 操作系统中不合法的文件名特殊字符（例如 `\ / : * ? " < > |`）。
2. **AI 智能重命名**：
   - 基于笔记的正文内容与分类，为被加工的笔记生成一个**简洁明了、高度概括**的新文件名（例：`我想把国外视频一键翻成中文_然后发现了这个_GitHub_1_万_Star_的开源答案.md` 重命名为 `GitHub万星视频一键翻译工具推荐.md`）。
   - 新文件名要控制在 10-25 个字之间，需要具有极高的可读性，能让人一眼看清笔记的大致内容。
   - 不要包含 URL 编码或无意义的随机哈希/多余数字。
3. **归档原件并添加 Aliases**：
   - 将原始文件移动到原笔记归档文件夹（备份目录）中，为了在检索时能一一对应，**其文件名也必须同步重命名为 `{新文件名}.md`**。
   - **绝对不容忽略的一步**：在加工后的新笔记的 frontmatter 中，**必须强制新增 `aliases` 属性**并记录原始文件名（不需要 `.md` 后缀），如：
     ```yaml
     aliases: 
       - "我想把国外视频一键翻成中文_然后发现了这个_GitHub_1_万_Star_的开源答案"
     ```
4. **写入加工后笔记**：
   - 在加工笔记归档文件夹下，根据 `obsidian_note_categories.md` 中「一级分类 → 文件夹名称映射」表中的**完整文件夹名称**创建子文件夹（如果不存在）。例如，工具推荐类必须写入 `{06 已归档}/1. 工具推荐/`，而不是 `{06 已归档}/工具推荐/`。
   - 生成加工后的笔记文件（包含完整的新 frontmatter + 原始正文），以新的文件名写入 `{加工归档文件夹}/{映射表中的文件夹名称}/{新文件名}.md`。


#### 步骤 5：整理后自检与修复（强制执行）

整理写入完成后，AI 必须立刻对自己输出的 Markdown 文件结构进行一次**自我审计**，核对以下关键点：
1. **YAML 语法合法性**：检查是否所有以反引号（\`）、特殊标点开头的 `description` 或 `key_points` 列表项，都被**英文双引号 `" "`** 完美包裹，没有任何未闭合的引号。
2. **Aliases 字段核对**：检查 `aliases` 属性是否已经被正确写入，并且是否完整保留了该笔记处理前的原始文件名。
3. **分类合规性**：检查最终落盘的 `category` 是否严格属于在 `obsidian_note_categories.md` 里面定义的二级分类，不允许擅自造词。
如果在自检中发现任何 YAML 格式错误或遗漏，必须立刻重写并覆盖该文件，直到完全满足规范。

#### 步骤 6：无法归类的处理

如果笔记满足以下任一条件：
- 正文内容过短（少于 50 字），无法有效分析
- 内容不属于分类体系中的任何一级分类

则：
- **不移动笔记**，保留在原始待整理文件夹中
- 向用户报告：笔记名称、无法归类的原因、以及具体建议（如"内容过短，建议补充后再整理"或"内容涉及 XX 方向，建议在 `obsidian_note_categories.md` 中新增对应类别"）

## 注意事项
- 处理过程中**不修改笔记的正文内容**，只添加或更新 frontmatter 属性
- 文件操作前确认目标路径存在，不存在则自动创建
- 分类体系以用户 vault 中的 `obsidian_note_categories.md` 为准，每次运行时重新读取，确保用户修改后立即生效
- 遇到同名文件时，在文件名末尾追加时间戳后缀（如 `文件名_20240801`）避免覆盖
- 重命名与归档操作时，绝对不能将带有 URL 编码百分号（%）的文件名直接写入文件系统，必须在步骤 4 第一步彻底解码。
- 确保所有的 YAML 输出完全符合标准规范，特别是带反引号或标点符号的列表内容，必须用双引号包围。

# 第二阶段：知识库整理（LLM Wiki Compile）

## 概述

基于 Andrej Karpathy 的 LLM Wiki 构想，在 Obsidian vault 中构建和维护知识资产层。

核心理念：**不是每次提问时从零检索，而是预先把每份资料读透、提炼为互相链接的知识页面**。新资料进来就增量编译，知识持续复利增长。

三层架构：
- **原始来源层**（`06 已归档/`）：经本 skill 第一阶段分类归档的笔记，只读不改
- **知识资产层**（`04 wiki/`）：在确认范围内维护的概念/实体主笔记、来源摘要与洞察；保留人工补充
- **Schema 层**（`AGENTS.md` + 本 skill）：规则与约束

---

## 模式选择

根据用户的表达自动判断模式：

- **整理知识库**：用户说"整理知识库""提炼笔记" → 默认检查 Wiki 已有知识页的重复候选，并将需整合的旧页与新增/变化来源一起按对象归组处理
- **整合已有知识页**：用户说"合并重复知识页""整合同一工具的笔记"等 → 可单独触发历史检查；与默认整理使用同一套身份与整合规则，预览后按确认清单整合；不合并或删除归档原文与来源摘要
- **检查知识库**：用户说"检查知识库""健康检查" → 执行巡检
- **查询知识库**：用户提出关于知识库内容的问题 → 先查索引再深读

---

## 整理知识库（Compile）

### 步骤 1：识别来源变化与已有对象

先阅读 [知识主笔记整合规则](references/knowledge_merge.md)。同一对象维护一个稳定主笔记；来源层维持一原文一摘要，不能用文件数量减少代替知识整合。

1. 先读索引和日志，再运行 `python -X utf8 scripts/validate_wiki.py <vault>`，建立原文到摘要页的实际映射。日志不是完成状态的唯一依据。
2. 使用 YAML 解析器读取 `original_path`；按原文唯一映射核对，不能用两边文件数量相等代替覆盖检查。
3. 默认检查整个 Wiki 的已有实体/概念页及来源摘要索引，识别同物异名、重复描述、同名异物和缺少主笔记的候选；不得因旧页已编译或日志标为完成而跳过查重。待处理清单包括这些历史候选、新原文、内容变化的来源、占位/空摘要、解析失败、来源失效及用户确认需要重编译的旧页。通过 `source_refs` 和相关正文定位受影响主笔记；旧页无该字段时检索来源入链，不全量重写有效页。
4. 按标题、别名、对象标识检索候选，完整阅读拟整合材料，按身份证据确认是否同一对象。同名异物、功能相近、产品与插件等分别保留；不确定项进入待确认清单。
5. 输出每组的源文件、身份证据、主笔记路径、内容差异、版本/冲突及旧页和引用处理方案，确认后执行。读取或解析失败必须显式报告，不得转为空字典或“原始资料未提供”继续执行。

### 步骤 2：按组整合，按来源保留出处

在已确认范围内先维护每篇来源摘要，再对每组对象复用或创建主笔记；一篇来源可支持多个对象。来源内容不混写进其他来源摘要。

#### 2a. 创建摘要页（sources/）

先完整读取原文，使用 YAML 解析器提取元数据，不用正则逐字段解析 YAML。合法的多行标量、列表、引号、中文和日期都必须保留语义。依赖不可用或返回值类型错误时停止该篇。

- 优先复用并核对已有 `description` 和 `key_points`；没有这些字段时从正文提炼，不生成缺省占位文本。
- 修复旧页的元数据提取遗漏时，可以定点恢复已有摘要与要点并注明来源；这不等于重新深读全文或完成外部事实核验。
- 作者、日期、原始链接从解析后的字段转写。只有原文确实缺失才注明“未提供”；作者没有对应页面时使用纯文本，避免制造断链。
- 先验证一篇包含中文和多行字段的代表性样本，再批量执行。脚本以 UTF-8 文件运行，避免 PowerShell → Python 标准输入的隐式编码及多层字符串转义。

在 `04 wiki/sources/` 中创建一个以笔记标题命名的摘要页。格式：

```markdown
---
type: source
original: "[[原始笔记标题]]"
original_path: "06 已归档/分类/文件名.md"
compiled: YYYY-MM-DD
last_updated: YYYY-MM-DD
---

# {笔记标题}

## 核心摘要
（用 3-5 句话概括这篇笔记的核心内容和价值）

## 关键要点
- 要点 1
- 要点 2
- 要点 3

## 关联
- 概念：[[概念A]]、[[概念B]]
- 工具/人物：[[实体A]]

## 来源
- 作者：{从 frontmatter 提取}
- 发布日期：{从 frontmatter 提取}
- 原始链接：{从 frontmatter 提取}
```

#### 2b. 复用或创建知识主笔记

按照 [合并规则的身份边界与元数据](references/knowledge_merge.md) 确定对象，优先复用身份正确、内容完整且引用稳定的页面路径与 `object_id`。概念写入 `concepts/`，工具、软件、系统、项目、人物等写入 `entities/`。

- 新建或实质整合的主笔记使用 `knowledge_schema: 1`、稳定 `object_id`、`identity_evidence`、`aliases`、`source_refs`、`source_count` 和 `last_updated`；字段含义与示例以参考文件为准，有效旧页不强制全库迁移。
- 同一事实去重表述，互补信息按章节融合，保留条件、限制和独有经验；关键结论与步骤就近注明来源。不得把各篇摘要逐段拼接。
- 不同版本、平台和部署方式分别注明适用范围。复杂教程在主笔记提炼要点并链接完整材料，必要时预览独立专题方案。
- 身份依据来自已读材料，不因标题相似自动合并；别名不能替代身份核对，来源数不能当作独立证据数量。

#### 2c. 处理已有重复页与引用

仅处理确认清单中的重复知识页，按照 [旧页整合与验收规则](references/knowledge_merge.md) 保存可恢复副本、核对独有内容与人工补充、暂存验证，再提交并回读。

旧页默认保留为 `type: "redirect"` 的原生 Markdown 迁移入口，使用 `knowledge_schema: 1` 和 `canonical_path` 直接链接主笔记，不保留主对象标识与来源计数字段。确认范围内更新入链；逐项检查标题锚点、块引用、嵌入及 Markdown 链接。不能保持引用语义时保留旧页待处理，不默认删除。不把迁移入口当作新的实体或概念计数。

#### 2d. 冲突处理

如果新材料与已有 wiki 页面**观点冲突**：

```markdown
> [!WARNING] 观点分歧
> - **旧说法**：{内容}（来源：[[旧摘要页]]，日期）
> - **新说法**：{内容}（来源：[[新摘要页]]，日期）
> - **状态**：待用户裁定
```

不覆盖旧内容，并排展示，等用户确认。

### 步骤 3：更新索引

写入后先运行 `scripts/validate_wiki.py`，再逐篇核对本次摘要和原文的语义、关键要点及出处。脚本通过仅证明确定性检查通过，不证明事实准确。任何失败项都不得计入完成；据实际结果更新 `04 wiki/index.md`：

# 第三阶段：知识库检查（Lint）

### 检查项

1. **🔗 断链检测**：扫描所有 wiki 页面中的 `[[双链]]`，检查是否指向存在的文件
2. **🏝️ 孤岛检测**：找出没有任何入链的 wiki 页面
3. **⚔️ 冲突检测**：检查所有 `[!WARNING] 观点分歧`，包括缺少状态的块。没有用户裁定证据的均保留为未决；修复只补“待用户裁定”，不能自行裁定或删掉警告。
4. **📊 覆盖度检测**：按 `original_path` 唯一映射，检查遗漏、重复、越界或失效路径；区分建页覆盖和内容有效性。
5. **🔄 时效检测**：找出 `last_updated` 超过 6 个月的 wiki 页面
6. **内容门禁**：检查核心摘要、关键要点是否缺失/占位，原文已有元数据是否被错误丢弃；比较索引与首页状态，不能因文件存在而标为已完成。
7. **对象与迁移检查**：核对重复对象标识、来源清单、正文来源集合及迁移入口目标；同名/同义候选只报告，语义身份仍需阅读确认。
8. **结构验证**：运行 `python -X utf8 scripts/validate_wiki.py <vault>`，校验 UTF-8、YAML、必需属性、双链、来源计数。非零退出码或解析依赖失效表示未通过，不得改报零问题。

## 运行安全覆盖（强制）

本节优先于本文件中所有相冲突的说明。

### 预览与确认

- 不得自动创建任何 vault 目录、配置文件、分类文件或归档子目录。任一必需路径不存在时，只报告缺失项和建议路径，停止并等待用户的明确决定。
- 每次处理（含单篇）必须先做只读分析。收件箱归档清单包含源文件、原文件名、分类、加工版最终路径、原文拟移动路径、重命名及冲突/跳过原因；Wiki 编译/整合清单使用 `references/knowledge_merge.md` 的对象分组预览，不包含原文移动。
- 输出清单后不得写入、移动、重命名或创建文件夹。仅在用户明确确认该清单后（例如“确认执行”）才可执行；清单、文件或会话状态变化时必须重新预览并确认。

### 提交顺序

以下临时文件/移动原文流程仅适用于收件箱归档，不适用于 Wiki 修复。Wiki 编译和修复始终不改动 `06 已归档/`；在确认范围内定点修改已有 Wiki 页并保留其他内容。

对每篇已确认笔记严格执行以下顺序；任一步失败都停止该篇，保留源文件，绝不覆盖既有文件，并报告失败原因。

1. 读取源文件，保留正文（不含原 frontmatter）逐字内容，生成新的 frontmatter 和 aliases。
2. 在加工版最终文件的同一目标目录写入唯一临时 Markdown 文件；不得覆盖任何临时文件或正式文件。
3. 运行 `scripts/validate_note.py <临时文件> --source <源文件> --original-name <原文件名（不含 .md）>`；只有校验通过才能继续。
4. 将临时文件原子性重命名为加工版最终文件。最终文件已存在或提交失败时停止，且不移动源文件。
5. 重新读取并确认加工版最终文件存在后，才移动原文件至原文归档目录。移动失败时保留加工版、源文件不删除，并报告“加工版已生成、原文仍在源目录”。

处理报告必须分别列出“已提交加工版”“已移动原文”“失败/待人工处理”；部分完成不得标记为成功。

### 文件名与 YAML

- 文件名 URL 解码最多一次；移除控制字符与 `\ / : * ? " < > |`，合并空白，去掉末尾空格和点。结果为空、为 `.` 或 `..`、或是 Windows 保留名（CON、PRN、AUX、NUL、COM1–COM9、LPT1–LPT9，忽略大小写）时，停止并请求用户指定名称。
- 最终文件名不超过 80 个字符（不含扩展名）。冲突时使用 `-YYYYMMDD-HHmmss-###` 后缀并再次检查唯一性；绝不覆盖。
- 所有 YAML 文本标量一律用双引号，并转义反斜杠、双引号和换行；列表逐项写入。不得直接拼接来自原 frontmatter、文件名或正文的 YAML 值。
- 临时文件必须由 YAML 解析器验证；目视检查或猜测引号不构成通过。

## Wiki 首页更新规范（强制）

获准写入的编译/巡检修复完成后，刷新 `04 wiki/_home.md`、索引和日志。纯只读巡检只在回复中报告，不为了刷新首页而绕过确认。先读取 `references/wiki_home_template.md`，并严格使用其中的版式、数据来源和空状态规则。

- 保持“工作台 → 知识资产 → 最新动态 → 健康状态”的固定阅读顺序；使用紧凑表格、一个信息 callout、短句和清晰空状态。
