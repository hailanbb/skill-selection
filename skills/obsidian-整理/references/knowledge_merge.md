# 知识主笔记整合规则

在第二阶段识别对象、整合新来源或处理已有重复知识页前阅读本文件。目标是让同一对象有一个稳定的阅读入口；原文与来源摘要保留，文件总数不作为去重成效。

## 1. 身份与内容边界

先检索已有实体/概念页的标题、别名、对象标识和身份依据，再阅读相关正文。标题、标签、关键词相似只用于发现候选，不证明是同一对象。

| 材料关系 | 决策 |
|---|---|
| 同一个工具、软件、项目、系统、人物的互补介绍 | 归入同一实体主笔记 |
| 同一概念的不同解释与案例 | 定义、领域和范围一致才归入同一概念主笔记 |
| 简称、译名、正式名、旧名 | 有明确身份依据后作为别名；更名不改变已有对象标识 |
| 同名但所属组织、项目或含义不同 | 分开，标题加入必要限定；不得互设别名 |
| 功能相近的不同产品、原项目与独立 fork、产品与插件 | 分开并建立关系，不能按功能或名称直接合并 |
| 同一对象的不同版本 | 共用本体介绍，具体行为按版本、平台、日期标注 |
| 同一工具的复杂教程、部署、排错、案例 | 主笔记提炼有来源的要点；完整步骤优先留在来源，确需独立阅读时提议专题页 |
| 一篇材料描述多个对象或比较多个工具 | 向各相关主笔记提取对应知识，来源摘要仍只有一篇 |
| 同一名称的上位概念、具体实现、局部组件 | 分开解释层级关系；对象粒度不同不能合并 |
| 只有名字相似，无法确认身份 | 列入待确认候选，保留已有页；不猜测别名或对象标识 |

工具身份优先用材料中明确给出的官方仓库、官网产品路径、组织与产品关系确认；网站同域名不等于同一产品，独立 fork 不等于原项目。概念身份核对定义、学科/使用语境及范围。URL 变化或仓库迁移须有明确迁移依据，不能只因名称相似认定更名。

仅凭归档材料不足时说明缺口；外部核实是补充任务，必须记录实际查阅的出处与时间，不能把未经核实的推断写成事实。剪藏日期和本次更新时间不等于事实发生或生效日期。

## 2. 页面与元数据

保持 `06 已归档/` 只读、`sources/` 一原文一摘要；不要把多个 `original_path` 塞入一篇摘要绕过覆盖校验。合并发生在 `entities/`、`concepts/`，保留各来源的独立观点与上下文。

新建或本次实质整合的主笔记使用以下字段；有效旧页无需全库补字段。`knowledge_schema` 是整数，`source_count` 是整数，其余文本由 YAML 序列化器写入。例子中的示意文件必须替换为实际存在的文件，不能原样生成占位页。

```yaml
type: "entity"
knowledge_schema: 1
object_id: "entity:example-tool"
entity_type: "software"
aliases:
  - "示例工具旧称"
identity_evidence:
  - "来源甲的项目介绍与来源乙的部署说明明确指向同一官方仓库；详见正文身份依据。"
source_refs:
  - "04 wiki/sources/来源甲.md"
  - "04 wiki/sources/来源乙.md"
source_count: 2
last_updated: "2026-09-14"
```

- `object_id`：库内稳定、区分大小写的非空标识。优先复用已有值；新对象首次确认后赋值，文件更名不改标识。不得仅靠给重复对象换一个 ID 消除校验错误。
- `identity_evidence`：非空的依据说明列表，正文“身份依据”补充可回溯的来源双链。不是模型自报的置信分数。
- `aliases`：无重复的已确认名称列表，可空；不同对象不共用容易混淆的简称。旧文件仍存在时，不把其完整文件名同时设成另页别名制造歧义。
- `source_refs`：去重后的来源摘要路径列表，使用 vault 相对路径、正斜杠及 `.md` 后缀；不得含 `..`、绝对路径、锚点或显示别名。
- `source_count`：唯一来源摘要数，与 `source_refs` 及正文引用到的来源摘要集合一致。它不是独立证据数量；转载或同源重复材料须注明同源关系。
- `type` 为 `concept` 时省略 `entity_type`；实体类型可按对象使用 `tool`、`software`、`system`、`project`、`person` 等。专题通常留在来源中；确有独立知识对象时另建概念页，综合判断才使用 `insights/`，不制造同对象的第二个主笔记。

主笔记围绕内容组织：一句话定义、身份依据、概述、核心能力/详细说明、适用场景、使用与实践、限制与版本差异、相关对象、来源。人物或概念使用合适标题。缺少材料的章节不生成，必要的未知项明确说明。

## 3. 综合写作与来源

先建立“信息点 → 来源 → 版本/平台/日期 → 处理决定”的核对清单，再组织正文。该清单可进入本次预览或日志，不必永久添加到每篇笔记。

- 相同事实只表述一次，合并其出处；互补信息归入对应章节，不按文章依次追加整段摘要。
- 保留独有的条件、操作步骤、限制、反例和实践经验。精简措辞不等于删除细节；移至独立材料的内容必须有明确入口。
- 关键结论、限制和操作步骤就近标注来源摘要双链，文末保留完整来源清单；不能让读者猜一组参考资料各支持什么。
- 版本、平台或部署方式能解释的差异，分栏或分节展示适用范围。只有材料明确支持替代关系时，才把旧方案标为历史；较新文章不自动推翻旧文章。
- 仍无法解释的事实冲突或观点差异，用 `[!WARNING] 观点分歧` 并列旧/新说法、出处、日期和“待用户裁定”。未经裁定保留，不能因为新材料重复某一观点就消除分歧。
- 用户补充、个人经验、评价与事实区分保存；不以“AI 维护”为由覆盖。旧页无法区分内容来源时保守保留并标明待核对。
- 同一来源可能影响多个主笔记；来源修改、失效或撤回时，通过 `source_refs` 定位受影响页。失效不是删除其结论的依据，先标记并核查。

## 4. 预览、执行与旧页整合

普通“整理知识库”默认检查全库已有实体/概念页及来源摘要索引的重复候选，再处理新增/变化来源；不能仅因原文已映射、旧页已编译或日志标为完成而跳过历史候选。先读名称、别名、对象 ID、身份依据与摘要索引，对相似或不明候选完整阅读正文及必要原文；不把一次全量检查变成全量重写。来源是否变化以内容比对或已保存指纹为据，不只看日志和文件数。没有可用索引或元数据不足时补充只读检查，并明确实际覆盖范围。

“整合已有知识页”可单独触发相同的历史候选检查；普通整理也包含该步骤。两种入口均先确认候选身份，再给出具体方案。一个分组对应一份预览记录：

| 对象/身份依据 | 来源文件 | 主笔记最终路径 | 新增/去重/版本差异 | 旧页及链接处理 | 冲突/跳过 |
|---|---|---|---|---|---|
| 已确认对象及依据 | 实际路径列表 | 复用或新增路径 | 拟整合信息与内容差异 | 保留页、迁移入口、受影响引用 | 待决定事项 |

同时列出需新增的目录、备份位置、索引/日志/首页修改范围。遵循 SKILL.md 的预览确认规则，执行只覆盖已确认清单；不把一次编译授权扩大为全库去重或删除。

主笔记选择优先考虑身份正确、内容完整、已有链接及用户指定；尽量保留稳定路径和现有 ID。合并前逐页记录独有内容、未决冲突及人工补充，保存受影响文件的可恢复副本和原路径清单。备份放在已确认的 wiki 扫描范围之外，避免当作新知识页计数。

先在暂存副本完成拟变更内容及检查，再在确认范围内逐文件提交并回读。校验基线保留旧问题与本次新增问题的区别；本次新增问题或受影响页仍未通过，不得标记为完成。写入前比对预览版本；发现并发修改停止受影响组，不覆盖。多文件不具备整体原子性，失败时报告实际已提交文件及可恢复位置，不能假报全组成功或盲目覆盖回滚。

旧页默认保留为原生 Markdown 迁移入口，而不是删除。仅在内容、引用与兼容性已核对后转换；入口示例：

```markdown
---
type: "redirect"
knowledge_schema: 1
canonical_path: "04 wiki/entities/示例工具.md"
last_updated: "2026-09-14"
---

# 原页面标题

内容已整合至 [[04 wiki/entities/示例工具|示例工具]]。
```

迁移入口不是自动重定向，不依赖插件。不得带 `object_id`、`identity_evidence`、`source_refs`、`source_count` 主笔记字段；目标必须直接指向有效实体或概念主笔记，不能指向自身、另一个入口、来源页或库外路径。日志记录旧路径到主路径的映射与备份位置。

转换前只读检索 vault 内入链，区分普通双链、显示别名、标题锚点、块引用、嵌入及 Markdown 相对链接；修改仅限确认范围。必要时在原页保留旧标题、块 ID 及对应内容以维持引用和嵌入。`aliases` 不能代替这些检查。不能保留语义时继续保留原页，不宣称整合完成；不明外部链接不宣称已核验。

## 5. 验收、索引和幂等

- 逐项核对合并前独有信息的去向、来源对应、版本条件和未决冲突。确定性脚本不判断“是否同物”、事实真实性或信息有无丢失。
- `validate_wiki.py` 保留旧页兼容；对显式采用新字段的页面校验完整 schema、对象 ID 重复、来源路径/集合/计数与迁移目标。旧页没有新字段不等于已通过身份核验。
- 脚本仅校验双链文件目标，不模拟 Obsidian 别名解析，不验证标题/块锚点、嵌入效果、Markdown 相对链接。对本次实际受影响的上述引用逐项人工/应用内复核；不能完成时保留旧页并报告范围。
- 索引先列实体/概念主笔记，再列专题/洞察、来源摘要和迁移入口；保持现有索引完整性。有效主笔记与迁移入口分开计数，不能按文件总数宣称知识增长或重复减少。
- 首页四类资产仅统计相应 `type` 的页面；迁移入口不计入实体/概念资产，状态或日志可单独报告。覆盖率仍按原文到来源摘要映射计算。
- 判断无变更前须确认不存在待整合旧页；首次整合旧页即使没有新增原文，也属于实际内容与结构变化。同一输入在整合完成后再次运行，主笔记路径、ID、别名、来源集合、正文顺序应稳定；没有内容或实际检查状态变化，不重写页面或刷新日期。无变更运行在回复中报告，不制造首页/日志更新。

### 行为验收案例（语义检查，不冒充脚本测试）

1. 两篇“星桥”分别属于甲组织的笔记软件和乙组织的备份工具：分开并消歧。
2. “星桥”“StarBridge”明确指向同一项目，一篇介绍功能、一篇介绍部署：合成一主笔记，保留两篇来源，增加确认过的别名。
3. 同项目 v1 仅本地使用，v2 材料明确新增同步：标注版本；不将旧限制推广到 v2，也不删除 v1 的适用说明。
4. 同工具包含安装与故障排查长教程：主笔记保留各自入口及关键条件，不拼接成无边界长文。
5. 旧页含个人补充、未决冲突及 `#安装`、`#^step1` 嵌入入链：内容有去向，旧锚点/嵌入可用，否则保留旧页待处理。
6. 仅同名且没有身份证据：待确认，不建立共同 ID；不从搜索结果或常识填造材料未提供的信息。
7. 新材料无新信息：不追加重复章节，不变动对象 ID、来源计数及日期；若是新增来源，仅增补出处和必要元数据。
