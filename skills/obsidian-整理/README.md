# Obsidian 自动整理与归档技能 (obsidian-整理)

> 🤖 为 Obsidian 用户打造的 AI 驱动知识管理全流程技能。覆盖三大阶段：**笔记整理归档** → **知识资产编译** → **知识库健康检查**。

---

| 阶段 | 触发词 | 能力 |
|------|--------|------|
| **第一阶段：笔记整理** | "整理笔记""整理收件箱""归档笔记" | 语义分析、智能分类、AI 重命名、双重归档 |

## 🛠️ 首次初始化配置 (Onboarding)

首次触发时，AI 代理会依次询问以下配置参数（一次一问）：

| # | 配置项 | 示例 |
|---|--------|------|
| 1 | Obsidian 库本地路径 | `D:\MyVault` |
| 2 | 待整理文件夹名称（支持多个，逗号分隔） | `01 待阅收件箱, 02 Clippings` |
| 3 | 原笔记归档目标（处理完的原始文件备份目录） | `03 已整理` |
| 4 | 加工后笔记归档目标（AI 加工后的笔记归入目录） | `06 已归档` |

配置完成后自动执行以下检查：

- ✅ 确认 vault 路径存在
- ✅ 确认各文件夹存在，不存在则自动创建
- ✅ 检查 `obsidian_note_categories.md` 分类规范文件：
  - **不存在** → 从 `references/` 中自动复制默认模板到 vault 根目录（含文件夹映射表）
  - **已存在** → 读取用户自定义的分类体系（以用户版本为准）

> 💡 后续使用时无需重复配置，直接进入处理流程。

# 📥 第一阶段：笔记整理归档

> 触发词：`整理笔记` · `整理收件箱` · `整理 Obsidian` · `归档笔记` · `分类笔记`

### 模式选择

- **批量模式**（默认）：用户说"整理笔记""整理收件箱"等 → 扫描所有待整理文件夹，逐一处理
- **单篇模式**：用户指定了某篇笔记的路径或文件名 → 只处理该篇

---

### 步骤 1：读取笔记 (Scan & Load)

读取笔记的完整内容，包括已有的 frontmatter（如果有）和正文。

---

### 步骤 2：AI 语义分析与属性生成 (Semantic Analysis)

AI 深度阅读笔记内容，自动生成以下结构化 frontmatter 属性：

| 属性 | 生成规则 |
|------|---------|
| `author` | 从已有元数据提取，多个作者用 wiki link 格式（如 `[[作者A]], [[作者B]]`） |
| `description` | 中文总结核心内容，150 字以内，第三人称视角 |
| `source` | 从已有元数据提取原始 URL |
| `published` | 从已有元数据提取发布日期，格式 `YYYY-MM-DD` |
| `clipped` | 从已有元数据提取剪藏日期，格式 `YYYY-MM-DD` |
| `tags` | 分析文章主题，生成 3-5 个精准的中文标签词，不含 `#` 号 |
| `category` | 按分类规范判定的**二级分类**名称 |
| `key_points` | 提炼 3-5 个核心观点，每个用一句话概括 |
| `quality` | 评估内容质量（信息密度、论证深度、原创性），打分 1-5（5 最高） |
| `related_concepts` | 提取 3-5 个核心概念或知识领域关键词，用于构建知识图谱 |

**关键规则：**

- `author`、`source`、`published`、`clipped` 从原笔记已有 frontmatter 提取，**不存在则留空，绝不编造**
- 如果原笔记已有部分属性，**保留已有值，只填充缺失的**——不覆盖用户手动填写过的值
- **YAML 语法极度严格**：所有以特殊字符开头或内部包含冒号、引号的字符串值，**必须用英文双引号 `" "` 包裹**

---

### 步骤 3：分类定位 (Classification)

依据 vault 根目录的 `obsidian_note_categories.md` 中定义的分类体系进行匹配：

- **一级分类**：判定笔记的主要方向，并从文件中的 **「一级分类 → 文件夹名称映射」表** 获取**完整的归档文件夹名称**（含编号前缀，如 `1. 工具推荐`）

  > ⚠️ **绝对禁止省略编号前缀**！否则会产生重复文件夹。

- **二级分类**：判定更细粒度的类别，写入 `category` 属性
- 每篇笔记**只归一个分类**，以主要意图为准，次要主题通过 `tags` 关联

**护栏机制：** 若笔记正文小于 50 字或完全无法归入现有体系，则**留在原位不动**，在报告中说明原因并提出建议。

---

### 步骤 4：文件名处理、重命名与归档 (Rename & Archive)

#### 4.1 文件名预处理（防乱码）
- **URL 解码**：如果原文件名被 URL 编码（如 `%E6%88%91...`），强制解码为可读字符
- **去除非法字符**：清除 `\ / : * ? " < > |` 等操作系统不合法字符

#### 4.2 AI 智能重命名
- 基于笔记正文与分类，生成**简洁明了、高度概括**的新文件名
- 控制在 **10-25 个字**，具有极高可读性
- 示例：`我想把国外视频一键翻成中文_然后发现了...` → `GitHub万星视频一键翻译工具推荐.md`

#### 4.3 归档原件并添加 Aliases
- 将原始文件移动到原笔记归档文件夹（备份目录），文件名同步更新为新文件名
- **必须**在加工后笔记的 frontmatter 中新增 `aliases` 属性，记录原始文件名

#### 4.4 写入加工后笔记
- 在归档目录下，严格根据映射表中的**完整文件夹名称**创建子文件夹
- 将加工后的笔记文件写入 `{加工归档目标}/{映射表中的文件夹名称}/{新文件名}.md`

---

### 步骤 5：整理后自检与修复 (Self-Audit)

写入完成后，AI 必须立刻执行自我审计：

| 检查项 | 说明 |
|--------|------|
| YAML 语法合法性 | 所有以反引号、特殊标点开头的值是否已用双引号包裹 |
| Aliases 字段核对 | `aliases` 属性是否已正确写入并完整保留原始文件名 |
| 分类合规性 | `category` 值是否严格属于定义的二级分类 |

---

### 步骤 6：无法归类的处理

满足以下任一条件的笔记**不会被移动**：正文内容过短（< 50 字）或不属于任何分类。保留在原位并在报告中说明。

---

```
## 📋 整理报告

### ✅ 成功处理：X 篇
| 笔记 | 分类 | 质量评分 |
|------|------|---------| 
| 笔记标题1 | 工具推荐 / AI 工具 | ⭐⭐⭐⭐ |

### ⚠️ 跳过（无法归类）：Y 篇
| 笔记 | 原因 | 建议 |
|------|------|------|

```

# 🧠 第二阶段：知识库整理（LLM Wiki Compile）

> 触发词：`整理知识库` · `提炼笔记`
> 
> 基于 Andrej Karpathy 的 LLM Wiki 构想。核心理念：**预先把每份资料读透、提炼为互相链接的知识页面**，新资料进来就增量编译，知识持续复利增长。

### 步骤 1：识别待编译笔记

1. 读取索引与日志，并运行 `scripts/validate_wiki.py` 建立原文到来源页的实际映射。
2. 新原文、空摘要、占位内容和来源失效页进入待处理清单；不是只看日志或页面数。
3. 先预览、后确认；有效旧页不重跑。解析失败必须报告失败，不能当成原文缺字段。
4. 用 YAML 解析器读取已有摘要、要点和出处；字段确实缺失时才从正文提炼或注明未提供。

### 步骤 2：逐篇编译

对每篇未编译的笔记：

- **2a. 创建摘要页**（`04 wiki/sources/`）：3-5 句话概括核心内容与价值，附关键要点和来源信息
- **2b. 创建/更新概念页**（`04 wiki/concepts/`）：提取核心概念（如 RAG、知识复利），已存在则追加新来源
- **2c. 创建/更新实体页**（`04 wiki/entities/`）：提取工具、人物、项目等实体
- **2d. 冲突处理**：新旧观点冲突时并排展示，标注 `[!WARNING]`，等用户裁定

### 步骤 3-5：更新索引 → 追加日志 → 刷新首页

### 步骤 6：输出知识库整理报告

```
## 📋 知识库整理报告

### ✅ 本次编译：X 篇
| 笔记 | 摘要页 | 提取概念 | 提取实体 |
|------|--------|---------|---------| 
| 笔记标题1 | [[摘要页]] | 概念A, 概念B | 工具X |

### 📊 知识库当前状态
- 概念页：N | 实体页：N | 摘要页：N | 洞察页：N
```

# 🏥 第三阶段：知识库检查（Lint）

> 触发词：`检查知识库` · `健康检查`

### 检查项

| # | 检查项 | 说明 |
|---|--------|------|
| 1 | 🔗 断链检测 | 扫描所有 `[[双链]]`，检查是否指向存在的文件 |
| 2 | 🏝️ 孤岛检测 | 找出没有任何入链的 wiki 页面 |
| 3 | ⚔️ 冲突检测 | 检查所有观点分歧块，缺少状态也报告，不替用户裁定 |
| 4 | 📊 覆盖度检测 | 按原文路径唯一映射，检测重复、失效、遗漏与内容占位 |
| 5 | 🔄 时效检测 | 找出 `last_updated` 超过 6 个月的页面 |

> **重要**：巡检只报告问题，**不自动修复**。等用户确认后再执行。

# 🔍 知识库查询（Query）

当用户提出关于知识库内容的问题时：

1. 先读 `04 wiki/index.md`，定位相关页面
2. 按需深入阅读（不全量扫描）
3. 如有必要，回溯 `06 已归档/` 原始笔记补充细节
4. 综合回答，带 `[[页面名]]` 引用
5. **回填机制**：有价值的新综合判断 → 提议写入 `04 wiki/insights/`，经用户同意后执行

## ⚠️ 通用注意事项

### 笔记整理
- 处理过程中**不修改笔记正文**，只添加或更新 frontmatter
- 分类体系以 `obsidian_note_categories.md` 为准，每次运行重新读取
- 遇到同名文件追加时间戳后缀避免覆盖
- URL 编码文件名在处理时彻底解码
- YAML 输出严格符合规范

### 知识资产层
- `04 wiki/` 中所有文件由 AI 全权维护，人类只读不写
- 增量处理新笔记和用户确认修复的缺陷旧页；不重跑有效旧页
- 新建页面前先查重
- 所有 wiki 页面使用 `[[双链]]` 互连
- 资料里没有的东西，不许写进 wiki（不编造）

## 安全执行与专业 Wiki 首页

> 本节优先于本文中任何相冲突的旧说明。

### 文件处理

1. 先只读分析并输出源文件、分类、加工版路径、原文移动路径、重命名和冲突项。
2. 等待用户明确确认清单；目录、配置与分类文件缺失时只报告，绝不自动创建。
3. 将加工版写入同目录临时文件，执行 `scripts/validate_note.py` 校验 UTF-8、YAML、必填字段、aliases 与正文完整性。
4. 校验通过后提交加工版；确认可读取后才移动原文。任一步失败均不覆盖、不删除源文件，并在报告中标记为未完成。

### Wiki 首页

获准写入的编译或巡检修复完成后，按 `references/wiki_home_template.md` 刷新首页、索引和日志。纯只读巡检不写文件。首页使用原生 Markdown，展示真实资产统计、最近 5 条动态和健康状态，并与索引保持双链。

## 内容质量门禁（2026-09-07）

修复的失败模式：来源页存在、YAML 和双链正常，却只有“原始资料未提供摘要”的占位内容；原文实际上已有摘要和要点。旧流程只按页面数判断完成，缺少原文与产物对照，未能拦截生成时的字段提取遗漏。无法仅凭产物确认当时具体哪条临时脚本出错，因此不将正则转义问题写成已证实的唯一根因。

新版要求使用 YAML 解析器、先验证代表性样本、回读检查输出，并区分建页覆盖与内容门禁通过。不得用正则逐字段解析 YAML，禁止解析失败后静默使用空元数据。

### 安装与运行

Python 3.10+；在隔离环境安装依赖，不修改全局 Python：

```bash
python -m venv .venv
# Windows: .venv\Scripts\python；macOS/Linux: .venv/bin/python
python -m pip install -r requirements.txt
python -X utf8 scripts/validate_wiki.py "你的知识库路径"
python -X utf8 -m unittest discover -s tests -v
```

请将上述 `python` 换成隔离环境中的解释器路径。非默认目录可使用 `--wiki` 和 `--archive`；`--today YYYY-MM-DD` 用于可复现的时效检查。

- 脚本只读，不修改原文、Wiki、首页或日志。
- 退出码 0：确定性检查通过；1：有缺陷/漏映射；2：路径等运行条件不成立。依赖缺失同样非零退出，不能算通过。
- JSON 输出包括 `source_page_count`（建页数）、`mapped_original_count`（唯一映射）、`content_gate_passed`（内容门禁通过数）、问题及未决警告。
- 检查 UTF-8/BOM、YAML（包括重复键）、日期、双链、孤立页、来源计数、摘要/要点占位、元数据丢失、重复映射及越界路径。
- 未决观点分歧作为警告保留；缺失“待用户裁定”状态作为结构问题报告。
- **边界**：脚本不是语义或事实判官；通过后仍需逐篇核对本次内容。修复旧摘要可恢复原文已有元数据，但不能宣称完成外部事实核验。双链检查覆盖 Wiki 和归档层、检查文件目标，不核验标题锚点，也不模拟全部插件解析行为。

### 新增文件

- `scripts/validate_wiki.py`：只读 Wiki 门禁与巡检。
- `tests/test_validate_wiki.py`：合成中文用例，覆盖原文有数据而摘要占位、BOM/CRLF、多行 YAML、重复映射、解析失败等回归场景。
- `requirements.txt`：显式声明 PyYAML 依赖。
- 仓库 CI 在 Windows 和 Linux 运行回归测试；不包含个人知识库数据。
